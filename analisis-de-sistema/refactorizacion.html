1. Sustituir condicionales con Strategy

La calculadora decide internamente qué regla de mora ejecutar. Refactoriza para recibir una estrategia; conserva los resultados de las reglas ya existentes y deja las tasas en una política externa. Escribe la interfaz, dos implementaciones y el consumidor.

Código inicial

class Calculadora {
  calcular(tipo: string, capital: Dinero, dias: number): Dinero {
    if (tipo === 'fija') return calcularFija(capital, dias, politicaFija);
    if (tipo === 'tramos') return calcularTramos(capital, dias, politicaTramos);
    throw new Error('Política desconocida');
  }
}
Comparar con la solución y rúbrica

Propuesta de refactorización

// Esquema TypeScript: Dinero, Politica y los cálculos
// son contratos del dominio existentes, no flotantes monetarios.
interface EstrategiaMora {
  calcular(capital: Dinero, dias: number): Dinero;
}
class MoraFija implements EstrategiaMora {
  constructor(private readonly politica: PoliticaFija) {}
  calcular(capital: Dinero, dias: number): Dinero {
    return calcularFija(capital, dias, this.politica);
  }
}
class MoraPorTramos implements EstrategiaMora {
  constructor(private readonly politica: PoliticaTramos) {}
  calcular(capital: Dinero, dias: number): Dinero {
    return calcularTramos(capital, dias, this.politica);
  }
}
class Calculadora {
  constructor(private readonly estrategia: EstrategiaMora) {}
  calcular(capital: Dinero, dias: number): Dinero {
    return this.estrategia.calcular(capital, dias);
  }
}
// La composición selecciona según la política del crédito.
const calculadora = new Calculadora(new MoraFija(politicaFija));

La calculadora deja de conocer tipos concretos. La selección se mueve al punto de composición; no desaparece mágicamente del sistema. Strategy encaja porque varía el algoritmo. Factory podría complementar la creación, pero no sustituye el contrato de comportamiento. Las funciones existentes se conservan para no alterar resultados. Para mora por tramos, redondea solo al final y respeta la política histórica del crédito.

Rúbrica: 4 puntos

  • Interfaz común y consumidor que depende de ella.
  • Implementaciones independientes y políticas recibidas como datos.
  • Mismos resultados para los casos anteriores, sin modificar sus pruebas para ocultar errores.
  • Explicación de Strategy frente a Factory y de la selección fuera de la calculadora.

2. Componer cargos con Decorator

Una cuota base admite seguro y gasto de gestión fijo, opcionales y combinables. El código agrega una subclase para cada combinación. Reemplaza esa jerarquía por composición. Los cargos de este ejercicio son montos ya calculados y de la misma moneda.

Código inicial

class CuotaConSeguro extends CuotaBase { /* ... */ }
class CuotaConGestion extends CuotaBase { /* ... */ }
class CuotaConSeguroYGestion extends CuotaBase { /* ... */ }
Comparar con la solución y rúbrica

Propuesta de refactorización

interface Cuota { monto(): Dinero; }
class CuotaBase implements Cuota {
  constructor(private readonly valor: Dinero) {}
  monto(): Dinero { return this.valor; }
}
class ConCargo implements Cuota {
  constructor(
    private readonly interna: Cuota,
    private readonly cargo: Dinero
  ) {}
  monto(): Dinero { return this.interna.monto().mas(this.cargo); }
}
const cuota: Cuota = new ConCargo(
  new ConCargo(new CuotaBase(base), seguro), gestion
);

CuotaBase y ConCargo cumplen la misma interfaz. Cada envoltorio delega al objeto interno y añade un cargo; así se evitan clases para todas las combinaciones. Se asume Dinero inmutable con validación de moneda. El ejercicio suma cargos fijos: calcular intereses sobre otros cargos o definir prelación de un pago son reglas diferentes que este ejemplo no implementa.

Rúbrica: 4 puntos

  • Base y decorador cumplen el mismo contrato.
  • El decorador recibe y delega a otra Cuota.
  • Composición de dos cargos sin crear una clase para la combinación.
  • No usar flotantes monetarios ni confundir total con prelación del pago.

3. Desacoplar reacciones con Observer

MotorDeMora conoce las clases de correo, tablero y auditoría. Refactoriza para permitir incorporar otro receptor sin editar el motor. Explica además qué no garantiza un Observer en memoria.

Código inicial

class MotorDeMora {
  registrarEntrada(evento: EventoMora): void {
    correo.enviar(evento);
    tablero.actualizar(evento);
    auditoria.registrar(evento);
  }
}
Comparar con la solución y rúbrica

Propuesta de refactorización

interface ObservadorMora {
  alEntrarEnMora(evento: EventoMora): void;
}
class MotorDeMora {
  private readonly observadores: ObservadorMora[] = [];
  suscribir(observador: ObservadorMora): void {
    this.observadores.push(observador);
  }
  registrarEntrada(evento: EventoMora): void {
    for (const observador of this.observadores) {
      observador.alEntrarEnMora(evento);
    }
  }
}
class AuditorMora implements ObservadorMora {
  constructor(private readonly auditoria: Auditoria) {}
  alEntrarEnMora(evento: EventoMora): void {
    this.auditoria.registrar(evento);
  }
}
motor.suscribir(new AuditorMora(auditoria));
// Correo y tablero se adaptan al mismo contrato.

El motor depende de ObservadorMora y publica sin conocer el trabajo de cada suscriptor. Este esquema ilustra el desacoplamiento del PDF; no es una infraestructura de mensajería durable. Deben definirse errores de receptores, duplicados y persistencia según los requisitos. Tampoco hay que emitir entrada en mora repetidamente si solo se vuelve a consultar una cuota ya morosa.

Rúbrica: 4 puntos

  • Lista de suscriptores tipada con una interfaz.
  • Reacciones concretas fuera del motor.
  • Nuevo receptor agregado desde la composición sin editar el publicador.
  • Diferenciar notificación en memoria de garantías de entrega y controlar eventos duplicados.
